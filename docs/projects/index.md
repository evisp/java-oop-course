# The Project

*One application, one team, two sprints*

<p class="meta"><span class="badge">Teams of 2 to 4</span><span class="badge">Sprint 1 · 10 points</span><span class="badge">Sprint 2 · 20 points</span><span class="badge badge--accent">Sprint 1 demos 14 to 18 December</span></p>

In the lectures you watch a bank being built. In the seminars you build a university system that someone else designed. The project is where you decide everything yourselves: what the program is for, which classes it needs, and how they work together.

You build one application with the same team for the whole semester. Sprint 1 turns it into a working console program using Modules 1 and 2. Sprint 2 takes the same code and finishes it with Modules 3 and 4. You never start over.

## Choosing what to build

The [project ideas](ideas.md) page has ten ideas with a suggested design for each. You can take one as it is, change it, or propose something of your own that meets the same checklist.

Two domains are not allowed: a bank, because that is the lecture application, and a university system, because that is the seminar one. Using an idea in a domain you have not seen yet is the part that teaches you something.

Keep the idea small enough to finish. A program with five classes that all work is worth more than a plan for fifteen.

## Your repository

-   One GitHub repository per team. One member creates it and adds the others as collaborators.
-   Every member commits their own work, from their own account, throughout the sprint. The history shows who built what.
-   The README says what the program does, how to run it, and how you used AI tools.
-   Each sprint is submitted by tagging a commit. The [Sprint 1 brief](sprint-1.md#submitting) shows how.

## Using AI tools

You may use AI tools: to explain an error, to compare two designs, or to write code. **You own what you hand in.** At the demo, every member must be able to explain any part of the program and change it while we watch.

State in your README which tools you used and what you used them for. Work that nobody in the team can explain is graded as work the team did not do.

## How you are graded

Each sprint is graded in four areas. Three of them look at the code and the repository, and every member of the team gets the same marks for them. The fourth is the demo, where each person answers questions on their own, so it is graded per person. The demo carries the most weight.

If the commit history shows that one member did very little, their marks for the team areas can be lowered as well.
