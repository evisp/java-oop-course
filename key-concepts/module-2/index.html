    Designing with Objects¶

    Key concepts from Module 2, weeks 5 to 8

    Module 214 conceptsThe lectures

    Module 1 was about building one good object. These ideas are about several objects at once: which one owns a job, when two of them count as the same, and how to keep a program's parts apart. New cards appear each week with the lectures.

    Click a box to jump to its card.

    Week 5 · Objects working together¶

    Week 5

    Responsibility

    Explain it in your own words, then turn the card.

    Responsibility¶

    A job or a rule that a class owns. Deciding which class owns which rule is called assigning responsibilities. The usual answer is the class that holds the information needed to decide.

    // Bank holds every customer, so Bank owns the transfer rule.
public boolean transfer(String fromNumber, String toNumber,
                        double amount) {
    ...
}
    DelegationSingle Responsibility PrincipleL5.1 Object Collaboration
    Week 5

    Delegation

    Explain it in your own words, then turn the card.

    Delegation¶

    Asking the object that owns some data to do the work, instead of reaching into that data yourself.

    // Bank asks each customer. It never loops over their accounts.
for (Customer customer : customers) {
    Account account = customer.findAccount(accountNumber);
    if (account != null) {
        return account;
    }
}
return null;

    Often confused withReaching in. Calling customer.getAccounts() and looping in Bank works, and it puts the customer's job in the wrong class.

    Week 5

    Identity

    Explain it in your own words, then turn the card.

    Identity¶

    Two references point to the very same object. In Java, == tests identity.

    Account restored = new Account(number, 500.00);
System.out.println(account == restored);   // false

    Often confused withEquality. Two objects can be equal by the class's rule and still be two separate objects.

    EqualityReferenceL5.2 Object Equality
    Week 5

    Equality

    Explain it in your own words, then turn the card.

    Equality¶

    Two objects count as the same thing according to a rule the class defines in its equals method. A class that does not override equals falls back to identity.

    @Override
public boolean equals(Object other) {
    if (this == other) {
        return true;
    }
    if (!(other instanceof Account)) {
        return false;
    }
    Account that = (Account) other;
    return accountNumber.equals(that.accountNumber);
}

    Week 5

    Value and entity

    Explain it in your own words, then turn the card.

    Value and entity¶

    A value is equal to another when all its parts match, like an amount of money. An entity is equal to another when its identifier matches, like an account and its account number.

    // Account is an entity: only the number decides.
return accountNumber.equals(that.accountNumber);
    EqualityL5.2 Object Equality
    Week 5

    hashCode and its contract

    Explain it in your own words, then turn the card.

    hashCode and its contract¶

    hashCode returns a number that collections such as HashSet and HashMap use to choose a group, called a bucket, for each object. The contract: objects that are equal must have equal hash codes, so override both methods or neither.

    @Override
public int hashCode() {
    return Objects.hash(accountNumber);
}

    Often confused withEquality. Equal hash codes do not make two objects equal. Different accounts may share a hash code.

    Week 6 · One job each¶

    Week 6

    Single Responsibility Principle

    Explain it in your own words, then turn the card.

    Single Responsibility Principle¶

    A class should have one reason to change: one person, or one kind of request, can ask for a change to it. Named by Robert C. Martin; the S in SOLID.

    // Account, Customer, Bank: the rules about money change
// BankConsole: the wording or the menu changes
// ConsoleApp:  the way the program is put together changes
    ResponsibilitySeparation of concernsModel and user interfaceL6.1 The Single Responsibility Principle
    Week 6

    Separation of concerns

    Explain it in your own words, then turn the card.

    Separation of concerns¶

    Keeping code for different concerns, such as rules, presentation and storage, in different places, so that a change to one does not disturb the others.

    Bank bank = new Bank("Bank of Tirana");       // the rules
BankConsole console = new BankConsole(bank, input);
console.run();                                // the talking
    Single Responsibility PrincipleModel and user interfaceL6.1 The Single Responsibility Principle
    Week 6

    Model and user interface

    Explain it in your own words, then turn the card.

    Model and user interface¶

    The model holds the data and enforces the rules; it never reads input or prints. The user interface talks to people and turns their requests into method calls on the model.

    // The console asks, the bank decides, the console reports.
if (bank.transfer(from, to, amount)) {
    System.out.printf("Sent %.2f EUR.%n", amount);
} else {
    System.out.println("That transfer did not go through.");
}

    Week 6

    Enumeration (enum)

    Explain it in your own words, then turn the card.

    Enumeration (enum)¶

    A type with a fixed set of values, listed once in its declaration. No value outside the list can exist.

    public enum AccountType {

    CHECKING,
    SAVINGS,
    TERM_DEPOSIT
}

    Often confused withA set of String constants. The compiler cannot check text: "CHEKING" compiles.

    Enum constantType safetySwitch expressionL6.2 Enumerations
    Week 6

    Enum constant

    Explain it in your own words, then turn the card.

    Enum constant¶

    One value of an enum, such as AccountType.SAVINGS. Each constant is an object created once when the program starts, so it can hold fields and answer method calls.

    SAVINGS("Savings account", 0.0025),

AccountType.SAVINGS.getMonthlyInterestRate();   // 0.0025

    Type safety

    Explain it in your own words, then turn the card.

    Type safety¶

    The compiler's guarantee that a variable holds only values of its declared type. An AccountType variable holds one of the three constants, or null, and nothing else.

    AccountType type = AccountType.CHEKING;   // does not compile
    Enumeration (enum)L6.2 Enumerations
    Week 6

    Switch expression

    Explain it in your own words, then turn the card.

    Switch expression¶

    A switch that produces a value. Over an enum, the compiler checks that every constant is covered, so adding a constant points you at every switch you need to update.

    boolean allowed = switch (type) {
    case CHECKING -> balance - amount >= 0.00;
    case SAVINGS -> balance - amount >= 100.00;
    case TERM_DEPOSIT -> false;
};

    Often confused withThe switch statement, which runs code instead of producing a value and needs a default branch to compile in cases like this one.

    Week 6

    values() and valueOf()

    Explain it in your own words, then turn the card.

    values() and valueOf()¶

    Methods every enum has without writing them. values() returns all the constants in declaration order; valueOf turns text into a constant and throws an exception for text it does not recognise.

    for (AccountType type : AccountType.values()) {
    System.out.println(type.getLabel());
}
AccountType.valueOf("CRYPTO");   // IllegalArgumentException
